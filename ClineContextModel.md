# Модель работы с контекстом в Cline

Описание модели управления контекстом проекта [github.com/cline/cline](https://github.com/cline/cline) на основе официальной документации (docs.cline.bot) и исходного кода ядра (`@cline/agents`, `@cline/core`).

## 1. Единица контекста — «задача» (task)

Контекст в Cline не глобальный, а привязан к **задаче** (task/session). Каждая задача:

- начинается с промпта пользователя и **строит контекст по ходу диалога**;
- имеет уникальный идентификатор и отдельную директорию хранения;
- содержит **полную историю диалога** (transcript);
- отслеживает расход токенов, стоимость API и время выполнения;
- может быть прервана и **возобновлена** (`resume`) в другой сессии.

Философия: **одна задача = одна цель**. Если смешивать несвязанные цели в одном task, контекст «засоряется» и релевантность ответов падает. Для новой цели — новый task.

## 2. Из чего состоит контекстное окно

Контекстное окно модели (working memory на текущую задачу) наполняется:

- промптами пользователя и ответами Cline;
- содержимым файлов, которые Cline читает или редактирует;
- выводом команд и результатами вызова инструментов (tool results);
- системными инструкциями (system prompt), включая правила — Cline Rules, `.clinerules`;
- описаниями доступных инструментов (tools), MCP-серверов, окружения.

## 3. Структура контекста (архитектурный уровень)

В ядре (`@cline/agents` → `agent-runtime.ts`) контекст разделён на три логических слоя:

1. **Сохранённый транскрипт (saved transcript / history)** — «правда» о диалоге. Это массив сообщений `AgentMessage[]`, который хранится и переживает вызовы модели.
2. **System prompt** — собирается из системных инструкций, правил, описаний инструментов, MCP, информации об окружении.
3. **Подготовленный запрос (prepared provider request)** — то, что реально уходит провайдеру в конкретном вызове. Формируется хуком **`prepareTurn`**.

Ключевой механизм — **`prepareTurn`**:

```text
saved transcript
       |
       | turn preparation
       v
prepareTurn        ← здесь происходит конденсация/сжатие контекста
       |
       v
prepared provider request
```

`prepareTurn` может переписать сообщения и system prompt **только для текущего вызова модели**. Он **не меняет** сохранённую историю и не влияет на `AgentRunResult.messages`. Это важно: сжатие контекста — операция «на лету» перед запросом, а не изменение исходной истории.

## 4. Управление переполнением контекстного окна

В Cline несколько взаимодополняющих механизмов:

### a) Auto Compact (автоматическая суммаризация)

Когда диалог приближается к лимиту окна, Cline:

1. создаёт **сводку (summary)** всего произошедшего;
2. сохраняет технические детали, изменения кода и принятые решения;
3. **заменяет историю диалога на сводку**;
4. продолжает ровно с того места, где остановился.

Это видно пользователю как обычный tool call «summarization». Используется существующий prompt cache, поэтому стоимость ≈ как обычный вызов инструмента (платится в основном за генерацию сводки).

> Для моделей без поддержки этого механизма Cline **откатывается к стандартному усечению по правилам** (rule-based truncation), даже если Auto Compact включён.

### b) Восстановление при переполнении (context overflow recovery)

Если провайдер отклоняет запрос с ошибкой `context_window_exceeded`, рантайм:

- помечает поворот как «recoverable overflow turn»;
- **принудительно запускает конденсацию** через `prepareTurn`;
- повторяет запрос (один раз);
- если `prepareTurn` не настроен — бросает `ContextWindowOverflowError` с понятным сообщением.

### c) Восстановление при max-tokens (выход за лимит вывода)

Если ответ обрезан на лимите выходных токенов без полезного tool call:

- рантайм добавляет «nudge» — подсказку быть лаконичнее;
- повторяет поворот до `MAX_TOKENS_RECOVERY_LIMIT = 3` раз;
- счётчик сбрасывается при каждом прогрессе, чтобы не зациклиться.

## 5. Подсчёт токенов

Расход токенов оценивается через `estimateTokens` (в `@cline/shared`). Каждый task отслеживает токены, стоимость и время — это видно в истории задач (сортировка «Most Expensive / Most Tokens»).

## 6. Сохранение и восстановление контекста

- **Checkpoints** — git-снапшоты изменений файлов. Позволяют **откатиться к состоянию до суммаризации** — контекст физически не теряется.
- **Правка сообщения** до вызова суммаризации восстанавливает диалог к этой точке.
- **Resume tasks** — задача возобновляется с полным контекстом: загружается вся история, сверяются состояния файлов с чекпоинтами.

## 7. Внешнее хранение контекста — Memory Bank

Поскольку модель «забывает» всё между сессиями, Cline предлагает методологию **Memory Bank** — структурированные markdown-файлы в проекте (`projectbrief.md`, `productContext.md`, `activeContext.md`, `systemPatterns.md`, `techContext.md`, `progress.md`). Это «долговременная память», которая переживает сброс контекстного окна: перед началом новой задачи Cline читает эти файлы и «продолжает с того места».

## 8. Мультиагентность и контекст

В multi-agent командах **каждый агент имеет собственный контекст и инструменты** — координатор разбивает работу на подзадачи и делегирует специализированным агентам. Состояние команды персистится между сессиями. В `@cline/agents` контекст агента также изолирован: `prepareTurn` меняет только запрос текущего агента, а не общий транскрипт.

## Итоговая схема

```text
Пользовательский промпт / системные инструкции
        │
        ▼
System prompt + transcript (история)
        │
        ▼
prepareTurn (конденсация при необходимости)
        │
        ▼
Запрос провайдеру → ответ → tool calls → результаты → обратно в transcript
        │
        ▼
При переполнении: Auto Compact (суммаризация) или truncation (fallback)
        │
        ▼
Checkpoints / Memory Bank — долговременное сохранение контекста
```

Ключевая идея: контекст **постоянно пересобирается** из истории + системных инструкций, а при приближении к лимиту **сжимается** (суммаризацией или усечением), при этом исходная история сохраняется и всегда доступна через checkpoints/историю задач.
